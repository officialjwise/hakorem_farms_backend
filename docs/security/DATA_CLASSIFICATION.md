# HaKorem Farms Platform: Data Classification

Every kind of data the system holds, the level it is classified at, where it lives, who may read it and the rule for handling it from storage to deletion. A reviewer uses this document to answer one question about any column or file: what am I allowed to do with it?

Sources: the table dictionaries in `docs/data-model/*.md`, `docs/security/SECURITY_ARCHITECTURE.md` section 6, ADR-0012 (table classes), ADR-0022 (encryption and erasure), ADR-0024 (database roles), ADR-0017 (authorisation) and ADR-0006 (audit log). Statutory retention and the Data Protection Act duties that sit behind these rules are in `docs/security/COMPLIANCE.md`. Written 2026-11-13 in session B1.

## 1. Levels

| Level | Test question | Examples | Harm if disclosed |
| --- | --- | --- | --- |
| **Public** | Would we be content to see it on the storefront or in a newspaper? | Catalogue, published retail prices, product images, availability bands, the public contract | None |
| **Internal** | Does it describe how the business runs, with no person identifiable from it? | Stock levels, costs, margins, internal prices, thresholds, ledger totals, health data of the system | Competitive or operational harm; helps a fraudster plan |
| **Confidential** | Does it identify, locate or describe a person, or record what a person did? | Customer, supplier, investor and staff names, phone numbers, addresses, order history, the audit log, exception reports | Privacy harm to individuals, legal duty under the Data Protection Act, 2012 (Act 843) |
| **Restricted** | Would its loss let someone move money, impersonate someone or read everything else? | Bank and mobile money payout details, identity numbers, tax identification numbers of individuals, TOTP secrets, password and token verifiers, keys and secrets | Direct financial loss, identity theft, total compromise |

Rules for applying the levels:

1. **Highest level wins.** A row, file, export, log line or report that contains data of two levels is handled at the higher one.
2. **Derived data inherits.** An aggregate that cannot identify a person (a monthly sales total) is Internal. The same figure keyed by customer name is Confidential.
3. **Unclassified means Confidential** until a category in section 4 is added for it. A new table states its category in the migration (a comment next to the table class, ADR-0012), and a review blocks a table with none.
4. **The classification travels with the object.** Files carry it in `platform.stored_file.classification`; retention rows in `aud.retention_policy.classification`. Both use the values `PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `RESTRICTED`.
5. **Test and seed data are Public in level and must be synthetic.** Production data never enters staging, seeds, fixtures or a developer machine (`docs/security/SECURITY_ARCHITECTURE.md` section 11).

## 2. Handling rules by level

The baseline. A category in section 4 may add to these rules, never weaken them.

| Aspect | Public | Internal | Confidential | Restricted |
| --- | --- | --- | --- | --- |
| **Storage** | Any table or the public bucket | Authenticated database access; private bucket | As internal. Personal fields in immutable stores encrypted under the subject's key (ADR-0022). Backups encrypted | Column-encrypted (`*_enc`, AES-256-GCM envelope) or held outside the database. Never in `platform.setting`, an outbox payload, a job payload, a cache or a log |
| **Who may read** | Anyone | Authenticated staff with the module's read permission | The role named in section 4, plus the data subject for their own data. Ownership rule on every read (ADR-0017) | Only the use case that needs the value, under the permission that guards that use case; every decryption is an audit event with action `DECRYPT` |
| **Transmission** | TLS 1.3 | TLS 1.3. Never in a storefront response | TLS 1.3. Responses carry only the fields the caller's shape allows (customer and investor shapes, ADR-0029) | TLS 1.3. Write path only. No API response, notification, webhook, event or export ever contains the plaintext; reads return a masked form (`...Masked`) |
| **Logging and tracing** | Free | Identifiers and outcomes only. No request or response bodies | Identifiers only. Phone numbers masked to the last three digits; no names, addresses, emails or bodies. The scrubber removes the rest before the line leaves the process | Never logged, not even masked, except the dedicated `*_last4` display columns. The audit writer replaces secrets with `[redacted]` |
| **Export** | Free | Needs the report permission; audited | Needs `mdm.export.create` or the module's export permission. Bulk export needs step-up (fresh TOTP within five minutes). Every export is an audit event with its row count and appears on the daily exception report as `BULK_EXPORT` above the threshold. Delivered as a private `CONFIDENTIAL` file by signed URL expiring in 15 minutes | Never exported. A payout run uses the value inside the owning module and sends it to the provider server to server |
| **Signed URL lifetime** | Not signed | 1 hour | 15 minutes | 5 minutes, and issue needs the specific permission. Each issue is a row in `platform.file_access_log` |
| **Retention** | While published | The period for the category | The period for the category; personal data kept no longer than needed (Act 843 section 24) | The period for the category; keys kept as long as anything they protect |
| **Deletion** | Soft-delete or unpublish | Soft-delete (`MASTER`) or none (`LEDGER`, `DOCUMENT`) | Anonymise in place on an approved deletion request, or destroy the subject key; statutory records retained and reported to the subject | Destroy the key or overwrite the ciphertext; a value is never "soft-deleted" in place |

## 3. Data the system must never hold

| Data | Rule | Enforced by |
| --- | --- | --- |
| Card number, expiry date, security code, magnetic stripe or PIN block | Never stored, logged, cached or passed through the server. Payment uses the provider's hosted page or tokenised flow | No column exists for it. `pay.webhook_event.payload` is scrubbed before storage. Log scrubbing test (ADR-0022). Webhook payload fixtures are reviewed |
| Plaintext password, one-time code, refresh token, API key, session token | Shown once or transient; only a verifier is stored | `password_hash`, `token_hash`, `key_hash`, `code_hash`, `credential_hash`, `csrf_token_hash` |
| Key material (key-encryption key, data keys, HMAC key, signing keys) | Outside the database or wrapped | Secrets file; `platform.subject_key.wrapped_key` |
| Secrets in `platform.setting`, outbox payloads, job payloads, audit payloads, example environment files | Forbidden | Review rule, secret scanning, the audit writer's redaction |
| Production data in staging, seeds, fixtures, screenshots or tickets | Forbidden | Factories only (`docs/TEST_STRATEGY.md`) |

## 4. Categories

Two tables. 4.1 says what each category is, where it lives and who may read it. 4.2 gives the handling rule for the same ids where it differs from the level baseline in section 2, and always states retention and deletion. Retention periods that come from statute are marked and sourced in `docs/security/COMPLIANCE.md`; the others are design defaults set on 2026-11-13 and change only through `aud.retention_policy`, an audited `MASTER` table.

Roles are the ten in ADR-0017: Owner, Manager, Accountant, Storekeeper, Cashier, Sales, Vet or Farm Hand, Driver, Investor, Customer. "Own" means the ownership rule in ADR-0017 restricts the read to records belonging to the caller.

## 5. Recorded exceptions and known limits

These are places where the data model as written does not match the rule above, or where an immutability rule limits what deletion can do. They are stated here so that nobody discovers them in the middle of a deletion request. Each is reported to the lead as a gap in the B1 report; none changes an ADR.

| Ref | Statement |
| --- | --- |
| E-1 | `bil.billing_document.customer_tin` is a plain `text` snapshot of the number as printed (`docs/data-model/bil.md`), while ADR-0022 lists tax identification numbers of individuals as encrypted and the E-VAT guideline says an individual's TIN is their Ghana Card PIN (`docs/security/COMPLIANCE.md` section 5). Until the data model changes, the column is treated as Restricted: never logged, never exported except on the document itself, readable only through `bil.document.read`. The archived file in `doc.archived_document.render_data` carries the same value. The deployed disk and backups are encrypted, which is the compensating control |
| L-1 | `LEDGER` tables reject update and delete for every role (ADR-0012, ADR-0024). Personal data stored in clear in a `LEDGER` table (`del.proof_of_delivery.recipient_name` and coordinates, `quo.quote_acceptance.accepted_name`, `ip`, `user_agent`, `platform.audit_event.ip` and `user_agent`, `platform.file_access_log.ip`, `doc.archived_document.render_data`) cannot be anonymised by a retention job or a deletion request. The audit `before` and `after` values are the only immutable personal data encrypted per subject. These categories are retained for their period and listed in `retained_categories` on every deletion outcome. Changing that needs an ADR that either encrypts those columns under the subject key or narrows them |
| L-2 | `platform.subject_key.wrapped_key` is destroyed by a deletion request, but a backup taken earlier still holds the wrapped key, and a restore would bring it back. The restore runbook therefore re-applies every completed erasure before the system opens. To make that possible without trusting the restored database, each daily audit anchor is stored with the list of subject ids whose keys have been destroyed (ids only, no personal data) |
| L-3 | Retention actions `PURGE` and `ANONYMISE` in `aud.retention_policy` can run only on `WORK` and `MASTER` tables and on the named mutable columns of `DOCUMENT` tables. Any `DOCUMENT` column a retention job must overwrite is listed in that table's allowed-change trigger when the module is built. A retention policy row for a `LEDGER` table is only ever `KEEP` or `ARCHIVE_OFFLINE` |

## 6. Review checklist for a change that touches data

A pull request that adds or changes a column, file type, log field, event payload or export answers these in its description. The reviewer blocks on a missing answer.

1. Which category in section 4.1 is the new data? If none, the pull request adds a row here.
2. Is the level at least the level of its most sensitive field?
3. Is a Restricted value encrypted with an `*_enc` column, and is every read of it an audit event?
4. Is it excluded from logs, spans, outbox payloads, job payloads, notifications and the audit payload (or redacted), as its level requires?
5. Does the customer, investor or storefront shape omit it unless the caller owns it?
6. Does it have a retention row in `aud.retention_policy`, and is the deletion action possible for its table class (section 5, L-3)?
7. If it is exported, is the export permission, step-up and audit event in place?
8. If a file, is the classification set on `platform.stored_file`, and is the signed URL lifetime the level's?
